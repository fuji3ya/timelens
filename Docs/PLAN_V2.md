## Track C — コンテンツ制作（Phase 1〜2 と並走）

コードと別サプライチェーンとして管理する。**コードが Phase 2 を終える前に C-2 が完了していること。**

### C-1: エリア決定 【founder 判断・最初に必要な唯一の入力】
- founder の生活圏・徒歩圏で**反復現地テストが可能**な場所に限定する（フィールドテスト・観覧地点の安全確認・体験動画撮影はすべて現地作業のため）
- 1エリア・1テーマ（例: 昭和後期の商店街）・無料1 + 有料4 スポット
- 決定物: エリア名 / テーマ・時代 / Hero Scene 候補地点（現在との変化が一目で分かり、安全に立ち止まれる場所）

### C-2: Hero Scene 素材制作（生成AI・再構成/演出ラベル）
- **V1 の過去景ビジュアルは ChatGPT（gpt-image-2）生成の「再構成/演出」イラストで構成する**。権利＝自社生成物として台帳記帳（リードタイム数日）
- 権利交渉が必要な実在古写真（`recorded` ラベル）は **V1 から除外**。B2B 提案期・資料館協業時に追加する
- 信頼性の担保（Qwen3 指摘の吸収）:
  - スポット説明文では実資料（市史・郷土資料）を**出典として参照**する（写真そのものは使わない）
  - UI の 記録/再構成/演出 ラベル表示は v1 計画どおり必須
  - `Evidence.expressionLevel` は `recorded` を既に実装済み — 後から記録写真 tier を追加できる
- **生成ガイドライン（Gemma4 指摘・法務）**:
  - 実在する特定の建物・店舗を同定可能な精度で描き込まない（意匠権/パブリシティ権）。「その時代らしい typical な街並み」に寄せる
  - 実在ロゴ・商品・人物を含めない（CLAUDE.md §7 禁止事項どおり）
  - 特定の写真家・作品の模倣指示をしない
- 音: 環境音（雑踏・チンチン電車等）はフリー音源 or 生成。台帳記帳必須

### C-3: 現地情報収集
- 観覧地点の座標・方角・安全情報・観覧位置写真（founder 現地 or 地図で AI が下調べ→founder が現地確認）
- 車道・横断歩道・駅ホーム近くを観覧地点にしない（§8）

## フェーズ計画 v2

### Phase 1 — Discover / Spot Detail / 位置情報（v1 計画どおり）
MapKit 地図、スポットピン/一覧切替、現在地距離、位置拒否時の手動選択、Spot Detail 強化、文脈的許可。
**完了条件**: 位置情報あり/なし両方でスポット選択可、拒否で詰まらない、CI green。

### Phase 1.5 — ASC app 作成 + TestFlight 配布パイプライン【新設】
- ASC に app 作成（bundle `com.starvingeffort.timelens`）、GitHub Actions で ipa ビルド→TestFlight upload（ibiki / nani-japan で確立済みの macOS runner + ASC API key パターンを流用）
- アプリ名は仮称のまま登録可（正式名クリアランスは Phase 4）
- **完了条件**: main への push から founder の実機に TestFlight ビルドが届く。位置許可→地図→詳細を実機で触れる

### Phase 2 — 無料 Hero Scene: Mode A + Mode D（最重要）
- カメラ権限の文脈的要求、`ExperienceState` 状態遷移、Safety Gate
- **Mode A**: 現在カメラ映像 + 過去イラスト重ね、現在⇄過去タイムスライダー、合わせ目ガイド
- **Mode D（シネマティックフォールバック）を「おまけ」ではなく品質指標に含める**: フェード/音のタイミング・色調まで磨く（3D 無し V1 が「安っぽい写真合成」に見えないための主戦場）
- 資料ラベル + クレジット表示
- **DEV バイパス**: `#if DEBUG` 限定で位置チェックをスキップし任意写真でスライダー体験を検証可能に。**リリースビルドではコンパイルレベルで存在しない**こと（Gemma4 指摘）
- 体験ログ（判定用の最小ローカル記録）: スライダー操作回数・体験完了・所要時間
- **完了条件**: TestFlight 実機で、観覧地点に立って 30 秒以内に比較体験ができる。カメラ拒否で Mode D へ。CI green

### Phase 2.5 — 【ゲート】実機体験判定【新設】
- founder が現地で判定: **「15 秒以内に『うわ、すごい』が起きるか」**
- 定量補助: 体験ログ（スライダー操作回数・完了率）+ 可能なら第三者数名の TestFlight 定性
- **Yes** → 3D 無しのまま Phase 4 へ直行
- **No** → 原因を切り分け: 素材品質（→ Track C-2 再生成）/ 演出（→ Mode A/D 磨き）/ 立体感の欠如（→ ここで初めて 3D 投入を判断）

### Phase 4 — 有料ルートと StoreKit（v1 計画どおり + 名称クリアランス）
- StoreKit 2 非消費型、文脈型ペイウォール、復元、`EntitlementRepository`、ローカル StoreKit テスト
- **アプリ正式名クリアランス**: 「TimeLens」は仮称。商標・App Store 重複・ドメインを landscape-first で調査してから ASC 名を確定
- **App Store メタデータで「歴史的文脈に基づく再構成体験」であることを明示**（生成AIコンテンツのスパム判定回避、Gemma4 指摘）
- **完了条件**: sandbox で購入・復元、再インストール後の権利復元

### Phase 5 — ルート体験・共有・分析（v1 計画どおり + B2B 拡張性）
- 4スポット導線、Route Progress、共有用縦カード/比較動画、分析イベント（§8 の最小セット）
- **B2B への布石**: 実在古写真（`recorded`）を後から高精度配置できるコンテンツ構造を壊さない（Evidence 設計は対応済み。アセット解決層で tier 追加できることを確認）

### Phase 6 — フィールドテストとリリース（v1 計画どおり）
異なる端末/通信/時間帯の現地検証、権利台帳カバレッジ、App Review ノート、提出。

### Phase 3（旧）— RealityKit 3D 【P1 降格】
Phase 2.5 ゲートが No かつ原因が立体感のときのみ V1 に復活。それ以外は公開後の P1。

## 検証方法の原則（Phase 0 で確定した現実）

- **Windows にはコンパイラが無い**: 静的レビューは proxy。ground truth は CI（`xcodebuild test`）と TestFlight 実機
- push ごとに OPSEC ゲート（`scan-public-repo-opsec.py`、HIGH/CRITICAL = push 禁止）
- AR/カメラ/位置はシミュレータでも検証不可 → 実機でしか「完了」と言わない（✅/🔲 分離を維持）
- UI 品質は HTML モック先行（workspace design-reference-first ループ）→ SwiftUI 移植 → CI の UI テストスクショで parity 確認
